## 3. Shipped

### 3.1 A verifier could answer once in the lifetime of a trigger · `5acb026` · axis: correctness

The audit's only CRITICAL. `release_state` is **one permanent row per (owner, trigger_type)** —
`ensureReleaseState` returns the existing row and nothing deletes it — and
`verifier_confirmations` keyed on that permanent id. So the idempotency read asked *"has this
verifier ever answered on this trigger"* rather than *"on this release"*.

Three consequences, all silent, all on the **second** use: a stood-down false alarm makes every
previous verifier `duplicate` next time (on the 1-of-1 rosters the beta actually has, the second
emergency can never reach quorum); standing down from PENDING or GRACE cleared nothing, so a
2-of-3 carried a stale vote forward; and `received_denials` was missing from `UPDATABLE_COLUMNS`,
so no transition could ever clear it.

Fixed **without a migration** — all five paths that start a release already stamp `initiated_at`,
so the instance marker existed and the read is now scoped to it. A NULL falls back to the old
behaviour, which can only refuse an answer, never manufacture one.

🔴 **The suite covered this file heavily and could not see the defect.** The existing fixture
ignored every query parameter after the second, so a scoped and an unscoped read were literally
indistinguishable inside it. One test also asserted the defect deliberately — corrected in place,
not deleted.

### 3.2 122 findings, nine file-disjoint lanes · `e609231` · axis: correctness

🔴 **The largest single defect closed here is an ACCOUNT TAKEOVER.** The `standby-claim` and
`break-glass` credentials providers declared `existingUserId` as a *credential* and passed it
into `claimStandbyRole` / `redeemBreakGlass`, where it skipped all identity work and became the
claim's identity. **Anyone holding one valid unclaimed invitation code could POST it with any

never from the body.

were still open at the time. That was accurate and is the reason §3.3 exists.

### 3.3 The 19 review majors — three of them defects in the fixes · `b6ef089` · axis: correctness

The nine review agents raised **19 majors, 49 minors, 31 overclaims** against the previous
commit's diff. Nine lanes closed 74, disputed 11 with evidence, left 21 with reasons.

**Three of the majors were defects introduced by the fixes themselves.** These are the ones worth
carrying forward, because each is a shape this repo keeps meeting:

1. **The takeover fix honoured revoked sessions.** `callerUserId` decoded the JWE and returned the
   id with no `isSessionCurrent` check — so a stolen cookie that "sign out everywhere" had already
   killed could be laundered into a fresh valid session by POSTing any unclaimed code at
   `standby-claim`. The lever built after the 2026-08-12 incident was bypassed by the fix for the
   next incident.
2. **New copy promised a safety property the code did not enforce.** The triggers screen said a
   withdrawn arrangement "cannot be started", while `runHeartbeatSweep` selected armed rows with
   **no `trigger_type` filter** — so a legacy ARMED estate row still armed on the cron, in exactly
   the case that copy renders. The filter now exists where the mistake happens.
   ⚠️ `lib/domain/enums.ts` had recorded the opposite ruling; amended in place, conclusion
   deliberately unsoftened — `emergency` is user-selectable, so a deceased owner's emergency
   trigger still releases and still stays released. The filter closed a *withdrawn-capability*
   leak, not that.
3. **The failover guard still replayed writes.** `isPreSendConnectError` matched on message text
   *before* the error code, so an `ETIMEDOUT` whose message contained "connection timeout" still
   re-issued a non-idempotent write against the secondary — the precise defect the change claimed
   to close.

Also closed: an orphan census that failed on the audit rows `deleteAccount` **retains by design**
(it would have made `verify:orphans` permanently red on a *correct* cluster); a delivery-health
check that latched 503 for thirty days on one bounced address and sent the operator to rotate a
working key; an `aws-setup` remedy that would have provisioned a runtime principal with **no KMS
grants at all**; and a fabricated symbol cited as evidence in the journeys register.

Register work owned separately (registers are never edited from a lane): **D11 closed** — every
secret's age now dated, the ten Vercel-held values read from the Vercel API rather than asked for
(`createdAt == updatedAt` on all 26 production keys: nothing in production has ever been rotated).
`ratified.demo-accounts-never-sweep` **corrected against a live read** — it claimed a demo
advances through `/api/demo/simulate` "driven by a person"; production holds **zero** demo
accounts and exactly one TOTP secret, so nobody can. Editorial thresholds recorded as ratified.

### 3.7 `relay_ro` — a read-only production identity · `7cb11a7` · axis: infra

Both constraints on unattended work — no credentials, and no pushing master — traced to one root
cause: **relay has no non-production environment**, so "a credential" and "production access" have
been the same object. This addresses the symptoms cheaply; only D4 addresses the cause, and it
stays deferred.

IAM user `relay-ro` + `relay-ro-policy` granting `dsql:DbConnect` on both clusters **and nothing
else**, mapped to DB role `relay_ro` by migration 039, applied to both regions. SELECT on every
table; no writes, no DDL, and — the point — **no KMS at all**. `relay-dev` by contrast holds
`kms:Decrypt`. A leaked `relay_ro` key reads metadata and can never turn a ciphertext column into
a secret.

Proven rather than assumed, in both regions: a no-op write probe (`WHERE 1=0`, so a missing
permission check could not have damaged anything) returned 7/7 correct each time. Then the five
database-only verifications ran under it end to end.

**It unlocks FIVE scripts, not seven** — the operator had been told seven. `verify:iam` and
`verify:kms` read the AWS API rather than the database, and a credential living in someone else's
cloud has no business enumerating IAM. Corrected before anything was built on the wrong number.

⚠️ **Read-only is not harmless.** Emails, display names and vault item titles are plaintext
columns, so this is still production PII. Accepted trade, recorded in `PROJECT.yaml`.

**A gap it created and closed in the same change:** `verify:roles` checked two roles and would
have ignored `relay_ro` entirely. It now checks three behind a contract, and its summary line is
**derived** from that contract, because it had gone on saying "neither holds DDL" while three
roles were being checked.

### 3.9 `verify:iam` grew from one principal to three · axis: security · **built, not live-proven**

The sweep found two gaps in the IAM half of the wall, and both were the same gap seen from
different sides.

**(a) `relay-ro` was audited by NOTHING at the IAM layer.** `verify:roles` had exactly this hole
on the same day and closed it. The IAM side did not, and it is the side that matters more here:
the single property that makes `.env.ro` safe to place somewhere less trusted than this laptop is
that **its policy carries no `kms:*` action at all**, and that property was asserted nowhere.
`relay-dev` holds `kms:Decrypt`, so this is a real distinction, not a formality.

**(b) The check was hardcoded to one user.** `lib/ops/iam-wall.ts` now holds a `PrincipalContract`
per identity — what it must hold, what it must never hold, and *what a violation costs*, stored
beside the rule so the person who meets the failure learns what it means without reading the file.
`CONTRACTS` lists all three; `scripts/verify-iam.ts` iterates it and audits nothing else, so **an
IAM user absent from that list is audited by nothing** and adding one means adding a contract in
the same change.

🔴 **The KMS rule had to be a new kind of rule.** "No KMS" is not expressible as "does not confer
`kms:Decrypt`": a policy granting `kms:DescribeKey` decrypts nothing, passes such a check, and
still falsifies the sentence `.env.example`, the rotation runbook and `verify-roles.ts` all print.
So the forbidden unit is a whole **service**, not an action — check the claim that was actually
made. A test pins exactly that case.

The sharpest proof that this is per-principal and not one global rule set: the *same* document —
`relay-runtime-policy` v2, with its envelope statement — reads healthy for `relay-runtime` and as
a breach for `relay-ro`.

`relay-dev`'s KMS grant is **deliberately not asserted**. It holds one, and that is what makes
`relay-ro`'s absence meaningful — but the action list was never written down anywhere in this
repo, and pinning a guess would make the first live run fail on the checker instead of on the
account. The run prints every action it reads; pin it from that, in a commit.

**Proven by planted violation, twice**, in the shape this repo requires: neutering the
service-reach predicate turned 7 tests red; dropping `relay-ro` from `CONTRACTS` turned the
coverage assertion red. Both restored and verified byte-identical by checksum.

⚠️ **`built`, NOT `live-proven`. The script cannot be run from here** — it needs `.env.admin`,
which this pass did not have. Its imports and its loop are proven to load (it prints the first
principal and then exits 1 on an invalid-credentials error with the right guidance), and every
rule is proven against fixtures copied verbatim from the live policies. **Nothing has read the
real `relay-ro-policy` through this code.** Run `npm run verify:iam` with `.env.admin` before
treating the KMS assertion as a fact about the account.
