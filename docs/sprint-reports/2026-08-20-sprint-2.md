## 3. Shipped

### S2-1 · A durable per-account sign-in budget — `e446d43` · security

**Contract:** migration authored and not applied · budget per-account, decays, resets on success ·
absence of the table tolerated and never fatal · a lockout indistinguishable from a wrong code · a
named way back · red-green proven including the table-absent branch.

`db/migrations/036_signin_attempts.sql` + `lib/auth/signin-attempts.ts`, composed inside
`signin-throttle.ts` so the two layers are one choke point.

**The property that decides whether it is safe to exist at all:** it refuses only on a **number**.
`null` from the store means *cannot answer* — no migration, unreachable cluster, timed-out query —
and that is **not zero**. Treating null as a refusal would hand any DSQL blip the power to lock out
every owner at once, on a product whose promise is access at the worst moment. Memory stays the
floor, is checked first, and an unreachable database can neither add a refusal nor remove one.

**Deploy-order trap deliberately not repeated:** migration 029 threw when its table was absent and
took passkey sign-in down for four minutes. This detects `42P01` once, logs one line, latches, and
falls back to memory.

**The address is never stored** — `email_key` is SHA-256. The table must count failures against
addresses with no account (refusing to would reveal which addresses are real), so in plaintext it
would become a list of everyone anybody ever tried. Hashing costs nothing: an investigation hashes a
*suspected* address and searches.

**Append-only, no counter column** — a counter would be a 40001 write-write conflict on the failure
path of an auth control, and an upsert would want `ON CONFLICT`, which `lib/people/claim.ts` records
as having 500'd the first live claim.

**Proven:** 44 tests. The direction that matters proven by planting it — changing `durable !== null &&`
to `durable === null ||` turns the structural guard and seven behavioural tests red.

**⚠️ The guard caught itself first:** its migration check asserted the file does not contain
`ON CONFLICT` and went red on the migration's own *comment* explaining why it is not used. That is
`CLAUDE.md`'s own sentence happening inside the commit that quotes it. Comments are stripped now.

### S2-2 · The alarm of record is ruled — `506ce9b` · security

Branch **(b)**: the GitHub-hosted monitors are the alarm of record; in-app mail is advisory.

**Why that is an answer and not a shrug:** the case that looks worst for the in-app alerter — Resend
degraded — is *already* covered independently, because a Resend outage stops the delivery webhook and
that monitor reports it through GitHub. Both ways of making the alerter itself independent fail on
their own terms: persisting alerts for a monitor to poll puts the alarm behind DSQL (so it could not
report a DSQL outage, and it needs a migration); calling GitHub from the request path adds an
outbound dependency and a second secret to a handler whose first rule is that it must never throw.

**The half that was a real defect:** `sendEmailBestEffort` returns `false` when the provider refuses
and the reporter **discarded it**, so a 500 during a Resend outage was silent twice — the incident,
and the loss of its own alert. It now writes one distinctly-marked `ALERT NOT DELIVERED` line.

**Proven:** `lib/ops/alarm-of-record.test.ts`, planted both ways — removing the delivery-result read
(1 red), deleting a monitor file (3 red). It is a **coverage** check, not a liveness check, and says
so on its own face.

### S2-3 · The secret rotation runbook — `dbd7b0e` · documentation

Twelve secrets, a `Last set` column reading `unknown` throughout (written out, because *"how old is
this?"* being unanswerable **is** the finding), and a section per secret that is not routine.

**Three things established by reading the code**: `NEXTAUTH_SECRET` also signs step-up, WebAuthn and
