## 3. Shipped

### S1-1 · Sign-in has an attempt budget and a witness — `e32e15b` · security

**Contract:** `authorize` refuses over budget before the DB lookup · the refusal is indistinguishable
from any other failure · `GuessKind` gains `totp` and a failed code records a miss · the budget
resets on success · red-green proven · the per-instance limitation written down.

**Defect.** Owner sign-in is an email address and a six-digit authenticator code and nothing else —
there is no password. `authorize` did a DSQL lookup and a code comparison per attempt with **no
failure counter and no rate limit**. Three valid codes in a million against the skew window means an
expected hit in a few hundred thousand unattended attempts, and an owner session unwraps that
owner's items without step-up (correctly — step-up guards bulk export, recovery codes and account
deletion). Takeover was vault compromise.

**Why it reads as an oversight rather than a decision** — every *other* guessable credential here
already had a budget: `recipient-code.ts`, `verifier-code.ts` and `recovery-code.ts` each hold
`MAX_FAILED_ATTEMPTS`, `/api/account/step-up` calls `rateLimit`, and `break-glass` carries a written
argument for why ~59 bits needs neither. The six-digit code was the shortest secret in the product
and the only one with nothing attached. `guess-watch.ts` — written because *"a guess at a code that
does not exist left no trace at all"* — did not count it either.

**Proves it:** `lib/auth/signin-throttle.test.ts` (the counting) and `lib/ops/signin-is-throttled.test.ts`
(that the provider still calls it — a budget the caller stops calling is no budget, and the first
file cannot see that). **All three claims of the guard proven by planting the defect:** gate call
removed → 3 red; guess-watch call removed → 2 red; `recordSigninFailure` added to the lookup-failure
catch → 2 red.

### S1-3 · `verify:kms` — the third wall — `df38d32` · security

`verify:roles` and `verify:iam` protect **access** to data that, if they fail, still exists.
Underneath sits the CMK, and every vault is ciphertext plus a data key wrapped by it. Nothing
measured its state. **The failure this watches for is an erasure with no rollback** — and a key
pending deletion still decrypts, so every other signal stays green for the whole waiting period.

`lib/ops/kms-wall.ts` (pure verdict, in `iam-wall.ts`'s shape) + `scripts/verify-kms.ts` (three
read-only calls, under `.env.admin`). It asserts the **positive** half too: a policy granting nobody
fails. Rotation is compared against `ROTATION_INTENDED`, which records the *as-provisioned* state
rather than a recommendation — the finding worth alarming on is nobody having decided.

**Proves it:** 22 fixture tests, every rule planted in the state AWS would actually return, including
a scheduled deletion *with the key still enabled*, an empty policy, a deny-only policy, rotation
wrong in both directions, and the account-root delegation pattern **passing** (a check that cries
wolf on the correct default is one somebody switches off). `tsc` covers the script itself —
`scripts/` is in the tsc program — so the SDK command shapes are checked against real types.

Also pinned, because nothing was: `verify:roles`, `verify:iam` and `verify:kms` are `package.json`
strings, the same unchecked class that shipped two entries unable to start on 2026-08-19.

### S1-4 · The failover moves the data and not the key — `67b43ba` · documentation

`DSQL_USE_SECONDARY` reaches the us-west-2 database and then asks a **us-east-1** key to unwrap what
it finds. A regional KMS impairment makes every vault unreadable from both regions — and the shape
of that day is deceptive: the site is up, pages render, titles load, and **Reveal is the only thing
that fails**.

Written into `CLAUDE.md`'s failover invariant and `docs/backup-restore-runbook.md`, plus a **sixth
restore step**: unwrap one real item before calling a restore done, because step 3 verified that the
payloads survived and nothing about whether they can be opened.

`docs/kms-region-proposal.md` sets out three options and recommends **Option A** — accept until the
first arms-length customer — on this project's own sequencing rule. Two things it establishes by
checking: an existing single-Region CMK **cannot be converted**, and `vault_items.kms_key_id` is
`NOT NULL` since migration 001 and already read on the decrypt path, so the routing information a
two-key path would need already exists. **No code changed.**

### S1-5 · The security incident and breach runbook — `c0b6fe9` · documentation

Evidence first (verify the audit chain and record the result *before* touching anything), then
containment in order, then scope in writing, then notification.

**Two findings the writing produced, both by checking:**

1. **The zero-knowledge claim has an exception.** `users.totp_secret` is plaintext `TEXT` (migration
   003), not wrapped by the CMK. A database compromise reaches owner authenticator seeds even though
   it reaches no vault contents. A notice saying "we cannot read your data" without that is a notice
   that misleads.
2. **There is no bulk session revocation.** `bumpSessionEpoch` is per user, called from one place.
   Signing everybody out means rotating `NEXTAUTH_SECRET` — a global outage as well as a
   containment.

Named `security-incident-runbook.md`, **not** `incident-response-runbook.md` as the contract said:
`incident` already means a customer-facing feature (`/api/audit/incidents`) and an error beacon
(`/api/incident`) in this codebase. Deviation recorded rather than taken silently.
