## 3. Shipped

### I1 · security · `07b383f` — the live site is a database superuser

`relay-runtime-policy` grants the production IAM user **both** `dsql:DbConnect` and
`dsql:DbConnectAdmin` on both cluster ARNs — read from the live policy, not assumed — and
`dsqlIdentity()` returns `admin: true` whenever `DSQL_ROLE` is unset, which it is in production. So
every request served by relaystandby.com runs against DSQL as `admin`, with authority to `CREATE`,
`ALTER` and `DROP` every table in the product. Ladder item 2: an exploitable security defect on a
reachable path.

**Acceptance criteria and how each was met:**

| # | Criterion | Met by |
|---|---|---|
| AC1 | `relay_app` in both regions, IAM-bound to the principal production uses | migration 033; binding confirmed in `sys.iam_pg_role_mappings`, not inferred |
| AC2 | Full DML on all 25 tables **including `caregiver_leads`** | `has_table_privilege` sweep — `caregiver_leads` is the *only* table differing from `relay_dev` (SIUD vs S---) |
| AC3 | No DDL | database `CREATE`=false, schema `CREATE`=false, no CREATEDB/CREATEROLE/SUPERUSER |
| AC4 | App runs end-to-end under it | ⚠️ **NOT MET** — see below |
| AC5 | Additive; one env var to cut over, one to roll back | `docs/least-privilege-cutover.md` |
| AC6 | Default privileges set so a future migration cannot lock production out | `ALTER DEFAULT PRIVILEGES` in the same migration |

**Proven by:** `npm run verify:roles` — new, both regions, read-only, and **proven to fail in both
directions**: granting `relay_dev` INSERT on `caregiver_leads` ("the wall is open") and revoking
`UPDATE` on `vault_items` from `relay_app` ("the application cannot do its job"). Both produced
exit 1 in both regions, then were restored.

**AC4 is honestly unmet.** Nobody has connected *as* `relay_app`. The credential that authenticates
as it lives in Vercel and deliberately not on any laptop, so the handshake is untested. It is step 4
of the runbook and the first thing to watch at cutover.

### I2 · correctness · `0c0a05a` — a release could open with nobody reached, and leave no trace

`notifyRecipientsOfRelease` returns how many recipients were reached. Both release paths discard it.
Correct as far as it goes — a mail failure must never roll back a committed transition — but it
meant the count was computed and thrown away, so the outcome this product exists to prevent left no
record: `release_state` says `released`, nobody was told, and `/circle` shows `unknown`.
`sweepSilentVerifiers` does not cover it; that watches releases *waiting* on confirmations.

The guard is at the seam, not the two call sites, and it is the only place both numbers exist — the
caller gets `reached` alone, and `0` cannot distinguish "every send failed" from "nobody was scoped".

**Proven by:** `lib/notify/undelivered-release.test.ts`, pinned from **both** sides. Removing the
reporting fails the catastrophic case; relaxing the condition to `reached === 0` fails the
no-recipients case. Partial success stays deliberately silent.

### I3 · correctness · `9623742` — `verify:live` under the least-privilege role

The named gate, unrun since the split shipped. **50 assertions passed against production as
`relay_dev`** (17 + 14 + 19), zero privilege failures: signup, TOTP, step-up elevation and
server-side revocation, export, recovery codes, closure, standby claiming, two owners firing
emergencies, the contact picker, the owner UI at 390px.

This is the evidence I1 could not produce for itself. `relay_app` holds strictly more privilege than
`relay_dev`, so a walk passing under the tighter role is strong evidence the looser one suffices.
Row counts identical before and after — nothing left behind, checked rather than assumed.

### I4 · correctness · `4232365` — double-clicking the checkout button counted twice

`PriceCard` awaits a Stripe round-trip before navigating and showed the visitor nothing meanwhile.
Every press emitted `intent_clicked` **and** `caregiver_intent` — the ratified G1 numerator — and
opened another Checkout Session.

The guard is a **memoised promise**, not a boolean: a flag set after the await is set too late for
the case that actually happens, the second press arriving while the first is in flight. `InterestForm`,
the Lane-A surface measuring the same gate, has guarded its submit this way all along; this is the
one that takes money and did not.

**Proven by:** removing the memo fails 3 of the new tests (in-flight press, after-completion press,
fallback path). The rendered label is also pinned — it moved from JSX text to a template literal,
exactly the edit that silently ships `$$119`.

### I5 · correctness · `cb0e9cb` — the gate is specified in visitors; the instrument counted views

`PROJECT.yaml` says "N ≥ 100 qualified **visitors**". Both trackers fired on every mount, so a
reload, a back-press or a reopened tab counted again — and the two sides inflate on *different*
actions, so it is not a wash:

| Action | Inflates | Bias |
|---|---|---|
| Reload `/caregivers` | denominator | false **kill** |
| Reload `/caregivers/interest` | numerator | false **ship** |
| Double-click the price CTA (I4) | numerator | false **ship** |

Now once per browser session, scoped like the channel attribution beside it. **Fails open** — where
`sessionStorage` is blocked the event still fires, because possibly counting twice beats certainly
not counting at all.

**Proven by:** the helper's own tests, *plus* wiring assertions that the guard precedes the emit in
both trackers, and that `QualifiedTracker`'s channel/click-ID parking stays outside it. All three
wiring tests fail when the trackers are reverted.

## 4. Blocked

### BLOCKED: P3/P4 — the cutover itself

- **Category:** decision needed (production environment + IAM)
- **Goal:** stop the live site running as a database superuser
- **Stopped at:** everything in this repo is done. What remains is setting `DSQL_ROLE=relay_app` in
  Vercel (Production scope) and, after the app is observed serving normally, removing
  `dsql:DbConnectAdmin` from `arn:aws:iam::461293170793:policy/relay-runtime-policy`.
- **Attempt 1:** built the role, grants, default privileges and the verification, so the change is
  one variable rather than a project. Done.
- **Attempt 2:** ran `verify:live` under the tighter role to establish the grants are sufficient in
  practice, removing the "will the app still work" question. Done — 50/50.
- **Need from you:** set the variable, redeploy, watch the first authenticated request; then strip
  the IAM action. Full procedure in `docs/least-privilege-cutover.md`.
- **Est. unblock cost:** ~15 minutes, plus watching one request
- **Downstream:** nothing else in this sprint depends on it. The role sitting unused is harmless.
- **Partial work:** none — everything committed is additive and inert until the variable is set.

## 7. Recommended top 3 for the next sprint

1. **Do the cutover, then watch one request.** It is the only remaining step of a security fix that
   is otherwise complete, and it is fifteen minutes. Every day it waits, the live site keeps holding
   DDL rights it has never used.
2. **Watch `writerProven` flip false → true.** Sprint 4's dead-man's switch is deployed and still
   reports `writerProven: false`, because no real send has happened since — the e2e walks all use
   reserved domains that are refused at the send seam. Until one real message goes out, the switch
   is correct and untested in production. One deliberate send to an address you control settles it.
3. **J9 steps 5–7.** Twice deferred now. If the ad sitting happens and G1 starts producing numbers,
   this becomes the obvious next build; if it does not, that is itself the answer and this should be
   dropped rather than carried a third time.

**And the thing five sprints have not changed.** `wtp_evidence: none`, `demand_signal: none`,
invitations sent zero. What this sprint did was make sure that when the number finally arrives, it
will be the right number — three separate ways it could have been inflated are now closed. That is
worth doing before a flight, and it is still not demand.
