## 3. Shipped

### S4-1 · The compatibility rule — `35f4242` · documentation

**Two things settled by reading the code rather than by preference:**

**The context is `{ owner_id }`, and that is forced, not chosen.** `encryptForUpload` POSTs
`/api/kms/wrap` **first** and only afterwards is the item persisted and given an id — at the moment
the data key is generated there is no item id to bind to. And owner-scoping is what the finding is
about: the 2026-08-13 oracle was *cross-tenant*.

**Both unwrap paths already hold the owner id**, so the change needs no new query on either. Verified
by reading: the owner branch already selects `WHERE id = $1 AND owner_id = $2`; the recipient branch
already gets `ownerId` back from `evaluateRecipientUnwrap`.

**🔴 And the finding that matters most is an implementation that must not be built.** The obvious way
to handle legacy blobs — try with context, fall back without on failure — **re-opens the exact hole
the change closes**:

```
attacker submits a foreign wrapped_data_key
  → Decrypt with { owner_id: attacker }  → fails (good)
  → fall back: Decrypt with no context   → SUCCEEDS
```

Every test written against legitimate blobs would pass and the oracle would still be open. So the
era is a **stored fact**, read before the KMS call, never inferred from a failure.

### S4-2 · Migration 037, authored and not applied — `99924c1` · completeness

One nullable column. **NULL means legacy and there is nothing to backfill** — every row existing on
migration day was wrapped without a context.

⚠️ Which is the **opposite of migration 035**: `secret_kinds` also defaulted to NULL, but there NULL
meant *unknown*, because the server could not know what an existing blob held. Here it knows with
certainty. Same mechanism, opposite epistemics — and 035's whole D3 saga came from that difference
not being obvious.

**⚠️ A guard I had not met refused this commit, correctly.** `lib/ops/schema-columns-are-used.test.ts`
exists because `consent_artifacts` was written since migration 009 and read by nothing. A column no
code mentions is exactly what 035 shipped — inert for a day — so it fired on mine, which is inert
*by design*. Resolved the repo's way: an allow-list entry that argues for itself and **carries its
own removal condition**.

### S4-5 · Roll-forward and roll-back — `a75ac83` · documentation

**The point of no return is not where it looks.** Not the migration, not the deploy that starts
*reading* the era — it is the first row **written** with a context. Roll the code back after that and
those rows cannot be decrypted by anyone.

**Which forces the build shape:** the writing side must be separately switchable from the reading
side, so it is **three deploys, not one**, and the middle one (read the era, still wrap without) is
what a hurried plan skips and what makes the rollback possible at all.
