## 2. `verify:kms` — seen to pass, and seen to fail

First live run: CMK `b3af288c…`, `Enabled`, CUSTOMER-managed, `SYMMETRIC_DEFAULT`, no pending
deletion, policy still granting the runtime principal `GenerateDataKey` and `Decrypt`. The runtime
ARN was **derived from the key's own ARN** rather than configured, which is the part that would
have been wrong if the account-id parsing were wrong.

`ROTATION_INTENDED = false` was a *derivation* from how `docs/aws-setup.md` creates the key. The
live key reports rotation **off**. The pin matches reality, so a silent change in either direction
is now catchable.

**Three negative controls, all exit 1:**

1. a key id that does not exist → `NotFoundException`, reported as a finding rather than a stack
2. `KMS_KEY_ID` unset → refused before any AWS call
3. **`alias/aws/s3`** — a key that really exists and is not ours → the *policy* rule fires

The third is the one worth having: it proves the refusal is about the key's **state**, not merely
about absence. A wall checker seen only to pass has not been seen to work.

The single-Region note printed on the live run exactly as designed — as a **note**, not a failure,
because a check that fails on a knowingly-accepted limitation is a check somebody switches off.

## 3. The durable budget, and the contract nobody had written down

The unit suite could only ever reach the missing-table and error branches. With 036 applied, a probe
exercised the rest against production: clean address counts **0 not null**, three failures count
**3**, the window predicate both includes and **expires**, another address unaffected, a clear
removes every row, housekeeping runs. Census afterwards: **0 rows left**.

🔴 **And it disagreed with an expectation, which is why it was worth running.** The probe asked for a
1 ms window and got back the three rows it expected excluded. `make_interval` takes **seconds**, so
`windowMs` is ceiled — 1 ms becomes 1 s.

The code was right and the expectation was wrong. But nothing said so, and a contract nobody writes
down is one the next caller discovers the same way. **Rounding up is the correct direction**: a wider
window counts *more* failures, so the error falls on the side of refusing an attacker, and rounding
down could produce a zero-length window that silently disables the budget while looking healthy.
Now documented on the function and pinned by tests (1 ms → 1 s, 1500 ms → 2 s, 15 min → exactly 900 s).

## 4. `verify:live`, and a property of the release gate nobody had recorded

Full chain, `&&`-joined so the stamp is a side effect of success:

```
e2e-stepup 17/17 · e2e-multiowner 14/14 · e2e-ui 26/26 · e2e-reveal 20/20 · e2e-factors 17/17
chain exit 0 · stamped 2026-08-20T06:01:15.954Z @ 9002679
```

🔴 **Getting there found something.** The first attempt reported `25/26` on the UI walk and the next
two runs died outright with `ERROR: signup begin 429`. That reads exactly like a flaky test and is
not one:

**`/api/auth/signup` allows 10 per hour per client key. One full chain performs exactly 10 signups.**

So the first run consumes the entire budget and a second inside the hour is *guaranteed* to fail,
part-way through, with nothing saying why. Nothing in `CLAUDE.md` said so; it does now.

The limiter is per-instance memory, so **restarting `npm run dev` resets it** — the same
fresh-instance state a real release run begins from, not a weakening of anything.

⚠️ **And killing the shell did not kill the server.** After the first restart, `netstat` showed
**two** node processes listening on 3000, one of them the instance whose budget was already spent —
so walks were landing nondeterministically on a poisoned instance. That is written into `CLAUDE.md`
too, because it would produce exactly the same "flaky test" reading.

The sign-in source limiter added in S2-1 (45 per 15 min) has more headroom — ~11 sign-ins per chain
— but it is the same class, and roughly four chains inside fifteen minutes would trip it.

## 4a. After the merge — the last thing nothing had covered

`verify:roles` proved `relay_app` holds the GRANT on `signin_attempts`. Nothing proved the
**deployed runtime uses it**, and that is a different claim.

Against `relaystandby.com`, after the deploy went live: a failed sign-in for an address with no
account answered **HTTP 401**, minted **no session**, and left **exactly one row** in
`signin_attempts` — written by production connecting as `relay_app`. Row deleted afterwards; zero
remain.

> ⚠️ **The first attempt reported a false failure, and it was the probe.** It POSTed to
> `/api/auth/callback/credentials` when the provider id is `email-totp`, so NextAuth answered 400
> before `authorize` ever ran — no row *could* have been written. For about a minute the honest
> reading of the output was "production does not record failed sign-ins", which was wrong.
> A probe that cannot reach the code it is testing produces a confident wrong answer. The reference
> to copy was `scripts/e2e-stepup.ts`, which posts to the provider id and keeps a cookie jar.
