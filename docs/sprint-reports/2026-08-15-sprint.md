## 3. Shipped

### I1 · correctness · `4d19288` — A laptop cannot file a production incident

**Root cause.** `lib/ops/alert-address.ts` documented *"local and preview environments must not try
to mail anyone"* and implemented it by returning `undefined` when **no address was configured**.
That silently equates *unconfigured* with *not production*. In this repo they are opposites:
`.env.local` is a full production env file — CLAUDE.md says so outright, because Relay has no dev
database — so it carries `RESEND_REPLY_TO_ADDRESS` and a live `RESEND_API_KEY`. The one machine the
guard existed to stop was the one machine that satisfied every condition for sending. The existing
test only ever proved the unconfigured case, then described itself as covering "local and preview".

**Fix.** The environment decision moved into `opsAlertAddress()` — the file that already owns "where
does an alert go", so all three senders (`error-reporter`, `guess-watch`, `incident`) are covered
with **no caller changes**; each already treats `undefined` as do-not-send. The body now names the
environment instead of asserting production.

**The direction is the design.** Silence requires *positive* evidence of a non-production process;
anything unrecognised still sends. The obvious spelling — `VERCEL_ENV !== 'production'` → silence —
is the dangerous one, because `VERCEL_ENV` is a system variable a project setting can stop exposing,
and that day would mute every alert invisibly. A channel that has gone quiet looks exactly like a
healthy one.

| Acceptance criterion | Proven by |
|---|---|
| AC1 dev server with full prod config resolves no address | `alert-address.test.ts` "sends nothing from a local dev server, however well configured it is" |
| AC2 production unchanged | "sends from production, which is the whole point" |
| AC3 fail-safe: `VERCEL_ENV` absent + `NODE_ENV=production` still sends | "still alerts when VERCEL_ENV is missing but the build is a production one" |
| AC4 preview sends nothing | "sends nothing from a preview deployment" |
| AC5 reporter silent in dev, still logs to stderr | `error-reporter.test.ts` "sends nothing from a local dev server…" |
| AC6 body names its environment | "names the environment it actually came from, rather than asserting production" |
| AC7 structural — no ops module re-decides this | "no ops module decides for itself whether it is running in production" |

**Failed before, passes after:** the two suppression tests fail against the old resolver
(`expected 'ops@example.com' to be undefined`). The structural check was **proven to fail** on a
planted `process.env.VERCEL_ENV` in `lib/ops/canary.ts`, then reverted clean.

> One of my own new tests caught a distinction I had blurred: a **present** `VERCEL_ENV` is
> authoritative, so `VERCEL_ENV=staging` is positively-not-production and sends nothing. Only an
> **absent** `VERCEL_ENV` falls through to `NODE_ENV`. The test was corrected to exercise the real
> fail-safe branch rather than the one I assumed.

### I2 · correctness · `8395c50` — Turn migration 029's warning into a check

**The gap.** `migrate.ts` applies one named file and tracks nothing — *"Migrations are NOT tracked
in a table; pass the file you intend to apply."* Which migrations have reached which cluster is
recorded nowhere. Migration 029 anticipated this with a comment loud enough to shout
(*"⚠️ APPLY THIS BEFORE DEPLOYING THE CODE THAT USES IT… an ordering requirement with teeth"*), and
on 2026-08-15 the comment lost. This turns it into a command.

New: `lib/db/schema-manifest.ts` (pure, CI-tested, no credentials) + `scripts/verify-schema.ts` +
`npm run verify:schema`.

**Both regions, and that is the point.** Failover here is an env switch (`DSQL_USE_SECONDARY`), so a
migration applied to one region and not the other stays invisible until the day somebody flips it —
by definition a day something has already gone wrong. Checking only the serving region would
reproduce the bug class the script exists to catch.

| Acceptance criterion | Proven by |
|---|---|
| AC1 parser finds declared tables, ignores commented-out ones | 6 parser tests in `schema-manifest.test.ts` |
| AC2 compares manifest against `pg_tables`, both regions | live run below |
| AC3 non-zero exit on drift | planted migration → **exit 1**, both regions flagged |
| AC4 read-only by construction | only statement issued is `SELECT … FROM pg_tables` |
| AC5 live-proven | `24 tables declared · primary ✓ · secondary ✓ · exit 0` |
| AC6 parser tests fail on a planted violation | vacuous manifest trips 6 tests; unstripped comments trip the ghost-table case |

Deliberate scope: comments are stripped before parsing (migrations here quote DDL in prose to
explain what they decline to do), and indexes are out of scope (DSQL builds `CREATE INDEX ASYNC` in
the background, so an index can be legitimately absent after a correct apply). A check that reports
a false positive on a good day is worse than no check.

# Addendum — D1 ruled, and the least-privilege split (post-sprint)

Steve's ruling on D1 reframed it: *"only me acting in a sysadmin capacity should be able to write to
the database without going through the standard product features and APIs"*, with **one environment
until G1 is decided**. So the answer is identity and privilege, not environments.

## What the ground truth turned out to be

Worse than the sprint assumed, and it changes the story:

- `lib/db/connection.ts` minted `getDbConnectAdminAuthToken()` **unconditionally** — the live
  production app connected as DSQL `admin` with full DDL rights. It could `DROP TABLE`.
- `relay-runtime` held **both** `dsql:DbConnect` and `dsql:DbConnectAdmin`.
- Vercel's `AWS_ACCESS_KEY_ID` and the laptop's were **byte-identical** (`…PUJ6`). Not similar —
  the same principal.

So no layer, in IAM or the database, could distinguish the deployed product from a laptop. That is
why marking the lead email (I3) was the only honest option at the time.

## DSQL divergence found

`GRANT USAGE ON SCHEMA public` fails: **`feature not supported on system entity` (0A000)**. `public`
is a system entity on DSQL; the AWS documentation's example grants USAGE on a schema the reader
created, which is why copying it verbatim fails. Table privileges work normally. Recorded in `030`.
